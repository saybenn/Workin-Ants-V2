## Aligned boundaries and scoped prerequisites

- **Media / Privacy:** R050 and R057 agree on createMediaUploadSession → bounded upload → completeMediaUpload → status/readiness, private exact-version binding, manifest/hash validation, failed-scan denial and linked terminal attempts. No new `createExportArtifact` bypass is needed. Field-by-field serializer/executor coverage and actual adapter tests remain implementation qualification; legal disposition schedules remain external. Exact bytes/hash and current generation must be checked by the owner at use.
- **Interview / Calendar / Video:** R046 owns schedule/acceptance and predecessor-successor lineage; R049 uses typed parent references and opaque Calendar mapping; R051 independently versions Video room generations and requires fresh parent authority. A rescheduled Interview successor is a new parent, while infrastructure recovery can create a new generation under the same still-valid parent. Neither inherits old participant acceptance or credentials. P18 rejects new acceptance of elapsed slots without a timer-expired lifecycle. Missing numerical join policy/provider TTL qualification blocks only that video path; no new early-join benefit can be inferred.
- **Booking / Order / Review:** R042/R052 keep reported performance separate from adjudication and financial/review consequences. Completion/no-show aliases must normalize to performance allegations; Order and Review independently evaluate their policies. P19 participant conversation reuse does not expose internal dispute/moderation evidence.
- **Audit / cryptography:** R060 leaves unused Audit chain fields unpopulated. R064 describes mechanics for separately approved owner-scoped chains. These are not conflicting obligations: shared mechanics do not enable Audit hashing or anchoring by default. Keep an explicit pointer so an implementer does not manufacture a universal chain.
- **Holds / restoration:** R047, R054, R058 and R059 agree that clearing one restriction merely permits fresh owner evaluation; it never overrides another Hold, candidate opt-out, erasure, entitlement expiry, or current safety. Release is not restoration or fulfillment.

## Proposed Notification integration matrix

The following names are proposed versioned semantic intent/template registrations, not claims that a renderer or provider is implemented. They deliberately use minimal authenticated-context notices already described by the owners. Source owners issue intents after their durable transition; Notification validates the immutable template schema and current channel eligibility. Default payload for every row is `sourceOwner`, typed aggregate ID/revision, semantic intent ID, `templateKey/version`, resolved local User IDs, safe authenticated route, sensitivity, and safe event kind. No message text, resume, evidence, exact location, raw provider error, credentials, or external meeting URL is permitted. Domain-specific data is obtained only through the authenticated owner view. Display labels may be omitted rather than leaking identity/context.

| Intent / template key | Source fact / command boundary | Recipient authority | Allowed additional variables / exclusions |
| --- | --- | --- | --- |
| `message.new.v1` | Messaging `messaging.message_created.v1`, R054/055 | Source-resolved other current eligible participants; exclude sender and revoked members | Thread and Message reference only; no body/attachment URL. Revision/hidden events invalidate views; no newly invented edit/delete email. |
| `order.outcome.v1` | Order `order.outcome_changed.v1`, R052/055 | Current authorized buyer and seller for that Order; other source kind requires its own participant mapping | Safe operational outcome code; no financial claim or restricted dispute evidence. |
| `booking.schedule.v1` | Booking confirmed/rescheduled/cancelled events, R052 | Booking owner-resolved affected participants | Safe change kind and authenticated schedule link; exact place/meeting credential excluded. |
| `interview.invitation.v1` | Interview committed invitation/current schedule revision, R046 | Invited eligible Candidate and organization-side participants explicitly selected by Interview | Interview reference and safe proposed/scheduled kind; no raw candidate data. |
| `interview.schedule.v1` | Interview committed cancel/reschedule/replace, R046 | Current authorized affected participants; removed participant receives only separately authorized safe removal notice | Predecessor/successor references restricted by owner access; stale acceptance link must recheck schedule. |
| `application.status.v1` | Candidate committed participant-visible application outcome, R055 | Candidate or authorized Organization recipients selected for that outcome by Candidate owner | Generic status-change notice and application reference; not a public Candidate-search exposure. Exact supported outcome list must be registered in Candidate owner before enabling each one. |
| `privacy.verification_needed.v1` | Privacy durable request transition requiring verification, R055/056 | Verified route to the request subject as resolved by Privacy/Identity | Request reference and safe action-needed code; verification credential is not a generic variable. |
| `privacy.outcome.v1` | Privacy accounted terminal outcome, R055/056 | Authorized request subject/representative with current request authority | Safe terminal category and link; no sensitive exemption justification or other parties' data. |
| `privacy.export_ready.v1` | Privacy generation and exact Media version ready with complete manifest, R057 | Currently authorized export requester | Request/bundle reference only; never a persisted public URL or signed download token. |
| `security.notice.v1` | Identity committed security intent, R063 | Affected local User only; Notification resolves eligible verified channel | Generic security change and opaque authenticated-context link; OTP/recovery secrets remain Identity challenge delivery. |
| `supply.status.v1` | Professional/Marketplace committed status/remediation source intent, R035 | Owner-resolved Professional User | Generic status/remediation code, no Healthcare/provider/Hold details. |

Material proposal changes must be surfaced by Gig's current-revision presentation under P14; an external notification is not proof the latest terms were presented for acceptance. Participant-visible Dispute changes may reuse `order.outcome.v1` only when Order itself emits that fact; otherwise Review must register its own safe case intent with Order participant resolution. Do not silently relabel a Review fact as an Order event. Optional viewed/shortlisted, Location notices, Interview completion/no-show alerts and other undeclared business triggers remain disabled. This finite matrix does not make legal notice delivery legally sufficient.

Idempotency is one semantic source intent × resolved User. Channel attempts are children, not additional business intents. Changed payload under the same fingerprint conflicts. Source corrections create a new source revision/intent only where they produce an authorized new notification; transport retry never manufactures a new intent. Before rendering a protected route, recheck current owner access; a removed recipient may receive only a deliberately registered safe removal notice, never the old protected content. Provider/channel verification and approved final copy are activation prerequisites rather than alternative recipient policy.

## Proposed typed moderation registry and receipt mapping

Every instruction binds immutable decision/action ID, case/cycle, typed owner target ID and expected revision, approved effect code, actor/service authority, purpose/policy/evidence references, semantic effect key and correlation. The table uses existing owners/ports and does not add first-class target enum values. Typed downstream effect references may be carried under an existing valid primary decision target, per CL-09-R007.

| Typed target / supported effect family | Owner public execution boundary | Scope / restoration guard |
| --- | --- | --- |
| `Job`, `Organization`: publication suppression/restoration | Hiring SH-103 owner handler, R047 | Publication effects only; recheck current compliance, restrictions and lifecycle. Not ownership transfer or verification bypass. |
| `CandidateSearchProjection`: suppression/restoration | Candidate SH-103 owner handler, R047 | Current participation/readiness/permission and no erasure/restriction. Does not create a Candidate Hold target or change application status. |
| `Thread`, `Message`: restriction/restoration | Messaging SH-103 owner handler, R054 | Persist restriction provenance; current membership and sensitivity still gate use. No edit/undelete bypass. |
| `MediaAsset`, valid Media grant effect: freeze, revoke public exposure/grants, preservation, eligible file exposure restoration | `executeMediaModerationInstruction`, Media §10.7 | Source context and Media safety remain required. Restoring exposure does not revive an expired/revoked credential. |
| `DigitalDownloadAsset`, typed affected grant reference: disable/restore/revoke | `applyDigitalModerationDecision`; `revokeDigitalDownloadGrant` for identified owned grant effects | Bought terms/Order entitlement/current Media safety remain required; expired/revoked grants are not rewritten into active grants. |
| `CourseVideoAsset`, typed affected playback grant reference: disable/restore/revoke | `applyVideoModerationDecision` | Current owner entitlement/safety and valid provider receipt; no new product or live-room authority inferred. |
| `Review`: hide/remove/authorized restoration | Review owner commands including `removeReview` and authorized restoration under R026 | Restore only current eligible accepted revision, recompute existing reputation contribution once; no author-edit restoration. |
| `Offering`: valid moderation restriction/clearance | Marketplace owner SH-103 handler and R035 graph | Clearance returns to draft; ordinary fresh publish is separate. No Order snapshot rewrite. |
| Order/payout reusable stops | Hold owner command and typed action decision, CL-09-R007 / R059 | Not a direct Moderation write to Order or Payment. Each consequence owner evaluates the protected action; financial effect requires Payment path. |
| CL-01 Identity/Role/Consent/Track/Customer generic moderation | Unsupported under R063 | Named security, entitlement, Hold or lifecycle commands only, with their own authorization. Profile row existence is not registration. |

Registry completion still requires each currently unnamed handler above to declare its one exported owner port and schema version in the owner architecture. Naming those ports is an AI-resolvable architecture integration task; no product choice is needed. Unsupported target/action pairs remain unsupported. A future target is not enabled by a generic fallback or an enum extension alone.

| Owner result | Canonical effect receipt | Meaning |
| --- | --- | --- |
| accepted / queued | `acknowledged` | Durable instruction accepted; effect not yet proved. |
| applied | `completed` | Exact requested restriction/effect is durable; include resulting owner revision and effect receipt. |
| restoration applied | `restored` | New authorized restoration effect completed, referencing original restriction/effect; not original history edited. |
| already-applied | Original receipt state | Replay original durable receipt; if original pending, still acknowledged; never infer completion from dedupe. |
| unsupported / denied / stale conflict | `failed` with terminal/reevaluate classification | No mutation; original intent remains accounted. Conflict needs fresh owner facts and authorized decision where relevant, not silent overwrite. |
| retryable known failure | `failed` with retryable classification | Retry same semantic effect key according to owner policy. |
| unknown provider or owner outcome | Pending reconciliation, not completed/restored | Query/reconcile original effect identity before another dispatch; keep durable uncertain state/evidence. |

`restored` is an effect type/outcome for a new linked command, not a reversible switch on the original receipt. Moderation Report/Case action_taken requires all required successful effects under R058; a downstream Search/provider acknowledgment is insufficient. Partial multi-owner execution remains incomplete with its per-step receipts. Hold release and expiry are distinct owner effects and do not supply Moderation restoration authority.
