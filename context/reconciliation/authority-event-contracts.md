# Authority, source facts and event contracts — WA-R068 / WA-R069

Detailed architecture contract selected for canonical integration under WA-R068 / WA-R069. These contracts resolve semantic ownership and source/consumer mappings; they do **not** certify implemented interfaces, providers, RLS, schemas or frozen fixtures. Existing product rulings P01–P19 remain binding. This document is the detailed contract appendix; platform-architecture-rulings.md remains the integration authority.

## WA-R068 — Action catalog and minimal source facts

Role governs a code-first catalog keyed `owner.port.v1` (one action per concrete command/query, including separate read/write purposes); names below reference existing owner ports or expressly identified semantic command families. Identity owns action-bound step-up proof, Organization Hiring owns membership, Messaging owns participants, and each other Module owns its supplied fact record. Register each concrete endpoint before enablement; absent actions deny rather than inherit a catch-all. A port group below is not permission to invoke every command in its Module.

Every fact result binds `schemaVersion=1`, source owner, typed resource ID, source revision, actor/subject relationship, action/purpose scope and evaluation time. Missing/unavailable/stale facts are distinct from absent target and never authorize. The command rechecks expected source revisions or obtains a current owner decision before effect; event payloads and client assertions cannot be used as current authorization. Return safe reason codes without revealing existence of private targets. No universal foreign-repository fact loader is authorized.

Assurance codes: **B** = authenticated current authority and relationship, no new mandatory step-up merely for ordinary access; **S** = fresh Identity proof bound to actor/action/target/purpose, current security epoch and configured expiry; **A** = durable sensitive-access audit acceptance before disclosure. Codes combine, and all applicable consent, entitlement, Hold, Healthcare and source-lifecycle gates remain. Self statutory identity verification remains separate from S. Service execution uses its explicitly scoped, retained initiating authorization/command and current safety checks; it cannot invent a human step-up proof. Support has only registered view/intake/on-behalf actions; admin is not universal authority. A reviewer who needs financial/security/restoration powers needs that explicit action grant.

## WA-R069 — Committed fact registry and subscribers

Every published fact uses `eventId`, exact `eventName` below, `schemaVersion=1`, producer owner, typed aggregate ID, monotonic source revision, `occurredAt`, `effectiveAt`, causation/correlation IDs, and correction/retraction lineage where applicable. Owner state/history and outbox intent commit atomically. SH-045/046 provide delivery deduplication/outbox mechanics, never cross-owner lifecycle truth. Receivers deduplicate by subscriber+event ID and use effect-specific source/rule keys for business effects. Same event ID with different fingerprint is quarantined. A revision older than the accepted watermark cannot resurrect data; gap/out-of-order delivery requests a current owner snapshot or durable replay and stays pending when unavailable. Tombstones preserve revision/generation even if content is erased. A correction is a new fact, never mutation of published history.

Events are restricted server-to-server facts and not public/client broadcasts. Payload includes only subscriber-required fields listed below; split projections per subscriber when scopes differ. No raw resume/message, exact address, credential, report, provider token or restricted adjudication note. Realtime sends only minimal authorized invalidation after commit, authorizes current audience on subscribe/emission/reconnect, and immediately revokes removed audiences; protected refetch repeats current owner checks. SH-071 adapter/provider/channel capability remains unqualified, not promoted by naming events.

The following is the selected architecture registry. Slash-separated event names denote separate registered schemas with the same base fields, not aliases. Historical unversioned/example names are evidence aliases only: do not publish both as distinct facts. Where a dedicated command/receipt already handles provider synchronization, notifications, Privacy instructions or moderation effects, an event does not replace that contract. Unneeded candidate events remain unpublished. In particular, no Role-owned domain stream or authorization cache is introduced contrary to WA-R031.

## Reward qualification, correction and subject mapping

Gamification consumes through `recordEligibleActivity`; Sweepstakes through `issuePrizeEntry` after its own eligible-entry decision. Producers certify facts, never an award, prize entry, payout or tax recognition. Each evaluation retains source owner+typed ID+revision, subject User binding, program/rule version, evidence references, occurrence/effective time, qualification disposition and original effect reference. Logical award key is `(program, rule lineage, trigger, source owner, source ID, beneficiary User)`; revisions reevaluate that same logical award. A rule version change does not silently re-award old activity: historical replay requires explicit rule migration policy. Technical event deduplication alone is insufficient.

| Trigger | Authoritative fact and beneficiary | Required source evidence | Correction / no-effect condition |
| --- | --- | --- | --- |
| order_completed | `order.outcome_changed.v1`; buyer or seller User selected explicitly by rule; seller from Order's preserved Professional-to-User binding | full-Order committed qualifying outcome, source kind, outcome revision, participant mappings, occurredAt; Payment receipt only through Order | Booking report, Gig mirrored completion and payment callback are not second sources. Later Order correction/refund causes reevaluation of the original award, not unconditional clawback or fresh award |
| qualifying purchase / permitted Sweepstakes source | `order.purchase_qualification_changed.v1`; buyer User; no invented Professional for platform-screening Order | purchase amount/currency, supported source kind, completed monetary/outcome evidence references, immutable purchase policy basis, correction/refund lineage | Rule explicitly selects sources and timing. No paid advantage, purchased entries or odds boost; official rules and approved free participation route remain prerequisites under P04/P05 |
| high_rating_received | `review.reputation_changed.v1`; reviewed Professional's preserved owning User | individual eligible published Review ID/version, recipient mapping, rating and scale, eligibility basis; aggregate reputation alone insufficient | Unpublish/remove/correct reevaluates same review/rule effect. Threshold/rating aggregation belongs approved program rules, not architecture |
| profile_completed | `professional.profile_completion_changed.v1`; Professional owning User | Professional owner's versioned completion-policy evaluation and completed result, not created/status event | false/retracted result reevaluates source/rule effect. Multiple profile events never create multiple User-wide balances |
| delivery_on_time | `order.delivery_timeliness_changed.v1`; seller Professional's User for supported seller Order | Order-owned contractual deadline and immutable agreement revision, actual verified delivery time and source receipt, explicit supported completion basis/timezone normalization | Unsupported source, missing deadline, disputed/unverified delivery or mere Booking report produces pending/ineligible, never guessed on-time. Later corrected timing reevaluates same logical award |

Order owns the timeliness determination by comparing its contractual delivery basis with delivery receipts from the actual Booking/Digital/other approved source; it does not let a provider timestamp redefine the contract. No deadline is fabricated for Orders without one. Gamification applies a linked compensating ledger effect only when its approved correction policy requires it; compensation is idempotent and never rewrites history. Sweepstakes handles corrections through prefreeze eligibility reconciliation or its separately approved postfreeze correction/redraw policy; never remove frozen entries or redraw automatically. Tax recognition remains Payment policy, not event delivery time.

Activation gates: owner/consumer executable DTO fixtures, source revision and tombstone tests, outbox/inbox replay/failure tests, current authorization/RLS parity, service scopes, notification template qualification, and actual provider/SH-071 qualification are implementation evidence. Reward points/thresholds, official rules, prize/tax recognition and eligibility, jurisdiction/age/retention/consent legal requirements are separately approved policy/external requirements; unsupported programs/triggers remain disabled. This distinction closes the architecture mapping question without claiming these activation gates passed.
