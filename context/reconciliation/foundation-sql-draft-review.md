## Issues exposed by drafting: Brain review required before execution

**DRAFT-01 — service currentness has no physical source in this cut.** DatabaseActionGrant records servicePrincipal/securityGeneration, but none of the 40 models supplies the current authoritative service generation. Comparing two issuer-provided claims would not prove revocation. The helper therefore rejects service contexts. Recommendation: approve an Identity-owned, narrowly readable service-generation leaf adapter with a concrete durable source, synchronization/currentness rules and revocation tests. If that requires a private enforcement table or additional model, review that source change first. No such table/role/catalog was silently added.

**DRAFT-02 — fixed Customer and atomic worker checks exceed the approved direct read surface.** Worker CustomerProfile access is empty and the helper has only grant/minimal Identity reads. Exact Track guards additionally need facts such as whether a subscription was created in this transaction, exact current base binding and required immutable history. The reviewed worker SELECT columns omit several of these facts; TrackSubscriptionEvent even has no standalone SELECT. The draft preserves every approved Track column privilege and explicitly blocks the worker entry. Concrete invoker SQL expresses the required checks, but those queries are not claimed executable under the worker ACL. Recommendation: approve fixed owner-scoped Boolean validation ports with an enumerated minimal read surface, protected context/source/fence checks, no returned source bodies, no business writes, and a nonrecursive policy graph. Do not grant raw Customer repositories, whole-table SELECT, usage access, BYPASSRLS or SECURITY DEFINER writes to make tests pass. The schema-owner forced-RLS role is not used as an authorization bypass.

**DRAFT-03 — mutable sources without an owner CAS revision.** AgeGateAttempt, AgeGateBlock, TrackUsageReservation and PrivacyRestoreMarker have no revision despite generic UPDATE permissions. A repeat write cannot safely produce the required unique `(owner,aggregate,revision)` proof at revision zero. UPDATE for every non-versioned domain source is blocked (immutable models already deny it). Recommendation: review whether each is append-only with a new semantic row, or needs an explicit CAS revision. The approved schema remains unchanged. This is an implementation conflict, not a product question for the client.

These are deliberate denial gates with named review issues, not permissive placeholders. Consequently this draft is ready for SQL review and is **not ready for execution approval**. Closing an issue requires corrected source/SQL evidence and regression checks, not deleting its gate.

## SQL decisions and limits

- Immutable issuance-time tuple binding is unchanged: separately committed issuer row, actual session_user/backend PID/xid8, READ COMMITTED, expiry/revocation and actual Identity generation. Bind performs no grant update and takes no action lock. Protected action takes shared grant/Identity advisory locks; revocation and Identity mutation take corresponding exclusive locks. This permits CTX02's revocation to commit after bind but before action. A later transaction cannot reuse the old tuple even after rollback/savepoint failure. Lock behavior, deadlock/retry policy and snapshot races remain database tests, not parser conclusions.
- `bound_grant` returns a composite internally and is not executable by app/worker. Only the opaque binder and Boolean helpers are exposed. Private helper owns no tables and receives SELECT only on grants and two current Identity columns. It cannot issue/revoke grants or read arbitrary source repositories. RLS leaf policies for this NOLOGIN role do not call the context helper recursively.
- `allowedFields` has a proposed internal SQL capability encoding: `Model/rowKey/SELECT|INSERT|UPDATE/logicalField`, `Model/rowKey/UPDATE/@row`, and `Model/rowKey/revision/currentVersion`. UUID rows use id; UserRole uses `userId:role`. No wildcard. The separate protected owner/action/purpose/root target and immutable tuple still apply. This is SQL transport representation for Brain review, not a canonical SH wire change or client authority. Exact primary-target versions also compare sourceGeneration; there is no universal cross-owner sourceGeneration mapping.
- UPDATE RLS requires the exact row capability; the BEFORE trigger checks actual changed fields and prior CAS version. SELECT requires all columns visible to that database role to be in the protected capability, because PostgreSQL row policies cannot determine which projection a caller selected. A partial field grant therefore fails closed. Future narrower projections/ports require explicit review. Column GRANTs are an outer maximum, never sufficient authority on their own.
- Source mutation, minimized closed prior/committed evidence, source PK/version, command owner/operation, server xid stamp, required Customer history and both message kinds are checked together at deferred commit. Reverse evidence guards reject orphan/fabricated source evidence. Infrastructure roots use specialized receipt/outbox/inbox/fence checks instead of evidence-of-evidence recursion. One aggregate revision cannot be written twice in the same owner transaction under this proof model.
- Owner code must preallocate identities, supply exact closed snapshots, implement semantic unique-conflict comparison and return original results. Correct fingerprint comparison is not implemented as a generic SQL upsert. Actor/step-up/Consent applicability, legal approval, external bytes/provider truth and public token conversion are owner-code responsibilities. The SQL does not pretend a submitted hash proves actual presentation or affirmative consent.
- Storage JSON digest is SHA-256 over PostgreSQL 17 `jsonb::text` encoded UTF-8; exact schema IDs/versions and model/message discriminators are checked. This is explicitly distinct from an unspecified wire digest encoding. All other F0 JSON fields must be SQL NULL. The source contracts stay byte-identical.
- Consent's composite FK and null-safe subject/action/context/hash checks are concrete. Draft content is denied; test-only content still requires a test-only owner authorization boundary and may not be used in production. Neither a legalApprovalRef nor a legal_approved enum constitutes external legal approval.
- Existing immutable receipts/history cannot be updated or deleted; same-key changed meaning conflicts via unique constraints and immutable guards. Valid existing Free/paid selections and usage cannot be modified by the enrollment worker. Usage mutation remains blocked until the actual period/reconciliation owner adapter qualifies. Privacy completion remains blocked until verified field-map/executor/full accounting and exact artifact evidence qualify. No invented deadline, privacy bypass or provider completion claim is introduced.
- Advancing the same principal's Identity generation invalidates its old grant for subsequent statements, including deferred proof checks. F0 generation-change fixtures must use a separately authorized unaffected Identity principal. A production self-service generation-change port needs its separately reviewed atomic continuation design; this draft does not weaken currentness to make that path succeed.

## Generation and offline verification

The exact directive command was tried first with Node 24.22.1 / Prisma 7.10.1 and the environment-free config. It returned exit zero but no SQL: the pinned schema engine (`d1b3f377ca835d73fd50954a5e22128b9ebdd6b8`) requires `--datasource <JSON>` at startup, while this CLI omitted it for a schema-only diff. This was diagnosed from engine stderr, not attributed to a database or P0-B.

An audited, exact-command-only Node preload (`scripts/sql-review/prisma-source-only-compat.cjs`) adds the literal empty JSON object `{}` to that engine startup. It supplies no URL, credentials, datasource source or shadow target, changes no installed package/config/lockfile and refuses other CLI arguments. The unchanged source-only command then produced the retained raw SQL. The initial failure and successful workaround are separate evidence in `foundation-sql-generation.json`. The temporary direct RPC diagnostic also used only empty/schema inputs and was not a different draft source.

`scripts/assemble-foundation-sql-review.py` assembles this review from the raw output, reviewed metadata/closed schemas and `scripts/sql-review/foundation-invariants.sql`; it does not invoke Prisma, SQL or a network. `scripts/check-foundation-sql-draft.py` is a separately scoped drafting-stage source/parser check. Historical candidate checks still enforce their historical pre-generation flags and all execution/adoption guards. New draft state is recorded in the P0-C-03 manifest. Parser validation includes PL/pgSQL bodies and SQL-language bodies, plus offline object/ACL/source preservation checks. It cannot prove catalog resolution, installation, function ACL behavior, row locking, RLS parity, recovery, migration replay or actual runtime success.

## Concrete source-correction recommendations for Brain

These recommended changes are **not installed or silently added to the approved 40-model source**. The current SQL denies the affected paths. Brain should approve/revise the exact following source changes before an executable version replaces those gates:

- **DRAFT-01:** add an Identity-owned private enforcement relation for current service epochs, with `service_principal` primary key, nonnegative monotonic `security_generation`, optional `revoked_at`, and an immutable Identity source receipt reference. It is a currentness leaf, not a database role/permission-policy catalog. Only the qualified Identity owner transition port may advance it; the issuer cannot manufacture its own current epoch. The existing NOLOGIN helper would receive SELECT only on service identity/generation/revocation fields. Bind/action compare the protected grant against that real row. Service action/revocation use the corresponding shared/exclusive advisory key and explicit revocation races. Bootstrap/rotation/crash/recovery authority and the exact additional SQL object must be reviewed with the source receipt protocol. No such relation or privilege has been created here.
- **DRAFT-02:** add separately owned NOLOGIN Boolean validation ports, rather than widening the current helper or worker. The Customer port needs only `id,user_id,status,archived_at,revision,privacy_generation`, a fixed CustomerProfile target, and the protected Track action/purpose. The Track atomic validation port needs the explicitly listed identity/state/typed-benefit fields already used in `track_enrollment_commit`, plus server mutation stamps and exact history-existence checks; no standalone history/Customer row bodies are returned. The port's role gets no DML, DDL, owner membership or BYPASSRLS. Its fixed leaf policies must call only protected grant/Identity helpers and must not recursively load owner repositories. Parameter/source/User/profile/revision/current work-fence checks are mandatory, and context/fence cannot come solely from a message or caller GUC. Enumerate and review each table/column before adding that role. Existing direct worker ACL remains byte-for-byte the approved Track column maximum. Install narrow fixed ports and their adversarial source/role tests before replacing the worker gate.
- **DRAFT-03:** make AgeGateAttempt and AgeGateBlock append-only in their access specifications; extending a block creates a new Identity-owned row with a new semantic identity. Add an owner-local `revision` to TrackUsageReservation and PrivacyRestoreMarker and to both their prior/committed evidence shapes; regenerate both candidate representations, SQL, access/test and fingerprint evidence consistently. Their atomic updates then use expected old revision and exactly +1. No source field or old validation result has been changed in this draft.

Server `updated_at` is stamped in the physical BEFORE guard, which permits the approved worker's narrow INSERT column list to satisfy native NOT NULL columns without granting timestamp writes. For registered SH-004/SH-114/Track successful command ports, the durable closed result body is required. Other F0 fixture/owner ports may retain SQL NULL result_body with required typed receipt identity/digest; non-null JSON is still restricted to the three registered response schemas. Exact reconstruction/replay of such a bodyless owner result is an explicit owner-code obligation, not an arbitrary JSON admission.
