# Hold applicability and source-readiness catalog — WA-R075

Classification: AI_RESOLVED_WITH_TRADEOFF. Hold owns applicability and release, while each source owns the condition and each consumer owns the consequence. Evidence: CL-09-R006/R007, WA-R023/031/059/062/068, existing ComplianceHold target FKs and owner action dependencies. This catalog makes those dependencies explicit; it does not expand supported primary target types or enact a new global suspension policy.

Request/evaluation binds `targetType`, `targetId`, `actionKey/version`, `sourceOwner`, immutable `sourceCauseId`, source revision, reason-policy version and evidence reference. An action catalog entry names its protected owner command. Owner adapters prove the requested resource belongs to the primary target before evaluation. A User or Professional hold cannot silently apply to every resource/activity of that person. Unregistered target/action/reason combinations cannot be created as active general-purpose holds; return unsupported. An existing ambiguous legacy hold requires scoped review; affected protected action fails closed until applicability is resolved, while unrelated actions are not indiscriminately stopped.

Reason values are source provenance, not an automatic action set. `admin_hold`, `other`, security reasons and provider reasons require the same explicit source/action policy and evidence; they are not wildcard authority. Identity security locks remain Identity lifecycle truth. Candidate/Application/Resume, Organization, Job, Media, Thread or other primary target extensions remain disabled until their typed representation and owner/action contract are deliberately registered; their existing owner-specific restriction mechanisms continue. No schema enum grants permission.

`getHoldReleaseReadiness.v1` accepts Hold identity/revision and source cause, then queries the registered source owner for `ready|not_ready|unavailable`, source revision, evaluated action/purpose, evidence reference and policy version. Multiple independent source conditions require all applicable readiness proofs. Release binds fresh Identity assurance for the specifically authorized reviewer, current target validity, expected active revision and retained source evidence. Support role alone cannot release. Source unavailable or changed cause cannot be converted into ready; a release request cannot release another independent Hold. Legal/provider constraints cannot be overridden by an administrative note.

After release, `hold.applicability_changed.v1` carries only opaque target/action/revision evidence. Each registered owner queries current aggregate facts and every applicable Hold again. Search consumes the source owner's eligibility/projection outcome, never direct hold-release permission. Audit preserves creation/evaluation/review/release provenance with restricted reason access. Privacy execution must still apply approved retention law; a Hold is not an automatic exemption or a bar to statutory access.

Alternative rejected: reason-to-global-ban lookup, consumer-local blocked flags, and direct financial effects on release would merge independent lifecycles. Explicit versioned action mapping is extensible without rewriting existing Hold history. Physical one-target constraints, legacy provenance reconciliation, source adapter schemas and concurrency/denial fixtures precede activation; the catalog does not claim migration completion. No automatic expiry deadline is introduced.
