# Gate 4 named bridge bindings — WA-R081

Architecture-only interfaces. These bind previously unnamed semantic responsibilities; no new Shared Operation identity, table, provider approval or implementation freeze is created. Existing ports with the same purpose must implement these semantics through one owner implementation, not a duplicate service. R017/R068 govern current actor, action, typed target, purpose, safe result and owner-issued opaque revision. The following schemas name semantic fields; physical DTO/transport encoding and runtime fixtures remain qualification work.

## Common protocol

Queries authenticate caller and authorized subject/context before returning existence-sensitive data. Input binds `requestId, callerContext, purpose, typedTarget, expectedSourceToken?` and a closed contract version. Results distinguish `available, denied, not_found, stale, unavailable, unsupported`; outward error projection must not leak protected existence. `available` includes `sourceOwner, sourceToken, asOf, policyVersions, permittedFieldSetVersion` and only the declared fields. A query is not mutation authority and an absent result is not a negative business fact. Consumers revalidate required current evidence at their action boundary. Revision mismatch reloads or conflicts; required unknown denies the dependent action.

Commands additionally bind semantic command identity, fingerprint and expected owner revision. Same identity/fingerprint returns its durable receipt; changed fingerprint conflicts. Commit owner history/receipt/outbox atomically. Transport acceptance, owner committed result and downstream completion are distinct. Timeouts reconcile the same identity before a new effect; no distributed transaction or foreign repository write. Required sensitive proof commits before disclosure; no private content/credential in receipts, events or diagnostics. Retention follows approved policy, not a new default duration.

## Customer obligations and composition

`queryCustomerObligations.v1` is implemented by each actual obligation owner, initially Order, Review/Dispute and Booking, for Customer archive/Privacy evaluation. Request binds Customer and User relationship, purpose (`archive_check` or authorized `privacy_retention`), bounded page size and owner snapshot/cursor. Response has stable owner snapshot, `obligations[{typedReference, revision, category, blocksArchive, retentionBasisReference?}]`, next cursor and explicit complete flag. It excludes narratives, money-provider details and unrelated people. Each owner defines the category and truth: unresolved commercial/fulfillment obligations at Order; active case/proof constraints at Review; remaining appointment/session obligations at Booking. Customer cannot cancel them. All registered obligations and pages must be covered before an archive conclusion; incomplete/expired snapshot restarts, not empty success. Privacy still owns legal disposition/exemptions. New obligation owners must register before their feature can create such obligations.

`getCustomerAggregateView` (existing SH-126) composes already authorized bounded owner read queries and reports each source as available/partial/unavailable with source revision/time. No global atomic snapshot is promised. Do not derive zero debt/no bookings/no cases from an unavailable source or use the dashboard as authority for archive. Historical source truth remains with each owner. A durable Customer projection is optional and unselected.

Notification's existing `listNotificationSubscriptions` / `revokePushSubscription` are the Identity settings integration. List returns opaque registration ID, safe device label, channel/status, generation and last-known time only for the current subject or a registered audited administrative action. Revoke binds recipient, opaque registration, expected generation and command key. Notification changes only its credential/dispatch state; a replaced generation conflicts/requeries. No endpoint/token, authentication-session mutation or security-completion assertion is returned.

## Classification acceptance and source input

`getClassificationSourceDescriptor.v1` is implemented by Professional, Marketplace, Organization Hiring (Organization and Job), and Candidate for only R070 registered target/purpose combinations and fields. No Gig, arbitrary Media download or raw resume input is registered. Missing capability or unsafe purpose returns unsupported/denied. R070 descriptor/version/allowlist is the response, not a new unconstrained `fields` bag.

`applyAcceptedClassification.v1` and `getClassificationAssignmentReceipt.v1` are contextual-owner integration bindings for R070, using its command/receipt fields and result vocabulary. Owner may delegate to its existing tag-edit command internally; external workflows do not write joins. Assignment includes expected source and assignment tokens, proposed canonical term IDs/revisions, proposal reference and current actor/review evidence. The receipt query binds original command and target, returns committed outcome/receipt/resulting tokens or unknown/pending, and reveals no foreign content. AI marks acceptance only from that receipt; timeout cannot justify a new mutation key. These names do not turn Taxonomy/AI into assignment owners.

## Screening and financial reevaluation

`getHiringScreeningContext.v1` is supplied by Organization Hiring and Candidate for their own parts of the same application/Job/Organization/subject relationship. It returns typed references, current owner tokens, requesting actor relationship, declared supported workflow purpose and eligibility facts; never a raw resume/report or a legal permissibility verdict. Trust verifies consistent bindings and separately evaluates required consent, applicable purpose, provider and approved screening policy. A subject mismatch, unsupported employer purpose or unknown relationship denies that screening path. Paid screening remains the approved distinct Order source, with no inferred employer sponsorship.

`reevaluateSettlement.v1` belongs to Payment. Authorized Order/Review sources submit immutable source-decision identity/revision, Order and financial-operation references and semantic request key. Payment queries current `getOrderSettlementFacts`, source decision/typed Hold release evidence and its own financial facts; result is a versioned `eligible|blocked|pending|unavailable` reevaluation receipt with safe blockers and current evidence references. It is **not** a payout/refund command. Actual dispatch still uses Payment's existing authorized financial operation and stable economic identity; refunds route through Order. Review closure, generic Hold release, failed query or replay cannot release money.

## Agreement and delivery receipts

`getOrderAgreementReadiness.v1` returns Order/purchase revision, required/not-required basis, applicable execution/document revision, integrity/finalization and signer-completeness decision, safe reasons and currentness. It does not return signatures/legal text. Booking consumes it before confirmation when the immutable source requirement demands Agreement. Only Order runs SH-112 `verifyAgreementDocumentHash` internally; Media stores/serves exact safe bytes and cannot declare execution readiness.

`getContextCalendarSyncState.v1` belongs to Booking's Calendar service. Request identifies authorized typed parent, desired parent revision and logical sync/cancel operation. Return mapping ID, requested/applied parent revision, `pending|applied|rejected|reconcile_required`, normalized effect receipt and safe error. It reads the same R049 durable mapping journal; no provider callback event or new Interview lifecycle is introduced. Interview polls/reconciles or consumes the original command receipt with the same binding. Late old revision cannot overwrite current sync state. Video uses the already named `getInterviewVideoRoomStatus` for corresponding generation-bound room results; no invented room-result event is required.

## Private Location and provider capability facts

`getLocationSourceFacts.v1` is implemented only by a source registered under R071 for its typed target and purpose. Professional/Marketplace/Gig/Hiring/Candidate/Interview own their fields and return exact input only to authorized Location processing, with protected source ID/revision, purpose, permitted field set, current visibility/relationship facts and sensitivity. This does not register every schema/search target or require collection of an absent address. Booking returns its Location source reference through `getBookingOwnerFacts`; Location-owned cache is not a second source. No approved source or configured precision means unsupported/unavailable, never a public exact fallback. Order checkout tax evidence remains the distinct R077 protocol.

`getProviderCapabilityEvidence.v1` is an owner adapter query, initially Media, Video, Calendar and Healthcare for the reviewed Healthcare bridge. It binds provider/account/environment/configuration revision, requested use case/data categories/purpose, capability-evidence references, effective interval and known/unknown state. It excludes secrets and cannot self-attest legal compliance. Healthcare combines actual adapter evidence with its current BAA/agreement/coverage policy. Healthcare owns its own BAA/e-sign adapter; there is no newly created universal e-sign owner. Unknown/expired/unqualified evidence blocks the sensitive provider path. Contract/legal/provider approval is still external.

## Privacy verification, outcome and backup evidence

`getPrivacyIdentityVerificationEvidence.v1` is Identity-owned and restricted to the authorized Privacy service/subject/action. Return immutable subject, verification attempt, method, issuer, assurance, purpose, verifiedAt, expiry/security-generation binding and evidence revision (R056); no raw credential, biometric, OTP or document. Privacy applies its approved verification rules and writes its own request result. Generic authenticated login is not assumed sufficient.

`recordIdentityPrivacyOutcome.v1` is an Identity-owned receipt command called by Privacy after a durable generation-bound outcome. Bind request/job/generation, subject, exact Privacy result revision, final/partial status, retained/exempt scope and minimized disposition references. Identity validates the source receipt and projects only permitted account markers, preserving immutable lineage; same key replays and old generation cannot overwrite a newer result. Accepted marker is not Privacy completion evidence. No final account deletion/security policy is invented; approved external policy and current retention obligations gate that action.

`getBackupDispositionEvidence.v1` belongs to the **platform backup capability**, not Privacy or a new domain Module. Ops is the operational integration steward for registering the selected backup executor and exposing its bounded receipt to Privacy; the executor alone produces storage/provider evidence. Input binds authorized request/generation and registered storage/backup scope. Return snapshot/backup-series scope, observation time, applicable policy revision, disposition (`pending_expiry|retained|purged|unverifiable`), effective expiry when verified, and immutable observation references. Coverage must state included/excluded restore points and replicas; unknown scope cannot imply purge. Privacy owns lawful response and any retention exemption, including truthful delayed completion. Restores must replay retained erasure/restriction dispositions before serving affected data. No purge command, retention period, provider support or legal approval is inferred. This assigns the missing integration responsibility; runtime placement and selected-provider verification remain Gate 5/8 and external qualification.

## Endpoint admission and qualification

Shared platform security owns SH-132 `enforceRateLimit` and common validation/error mechanics. Role owns registered authority/action/assurance policy; each caller owns its action-specific key scope, budget/window, bypass and failure posture under the Shared registry. Privacy/Location sensitive endpoints must register these values before activation and use non-enumerating outward errors; internal diagnostic references remain restricted. No numerical security policy is fabricated here and no local duplicate limiter is permitted.

For every binding, qualify closed schemas, freshness/authorization, denied versus unavailable handling, duplicate/conflicting command keys, partial snapshots, stale/late result races and sensitive field exclusion bilaterally before interface freeze. Architecture review is not executable validation. The final inventory lists implementation and external qualification separately.
